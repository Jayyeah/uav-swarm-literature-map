# READING NOTE — P0048 — Hybrid Control for Large Swarms of Aquatic Drones

## 1. Paper positioning
- Problem: large homogeneous swarms of inexpensive aquatic drones must execute long-duration maritime patrol/coverage while locally detecting and pursuing repeated intruders, with battery return/recharge integrated into the mission.
- Main predecessors: swarm robotics/evolutionary robotics and hybrid hierarchical control.
- Why this paper was needed: [原文] manually synthesizing scalable decentralized swarm behaviors is hard, while evolving one monolithic complex controller has bootstrapping/reality-gap problems; the authors therefore evolve behavior primitives and connect them with a hand-written state arbitrator.
- R-LIFE-01 role: [AI判断] closest **same-pool persistent-loop near miss**: the same homogeneous agents execute `Patrol → local alert/recruitment → Pursue Intruder → Patrol` under repeated intruder crossings. Its decisive missing edge is terminal capture.

## 2. Problem setting
- Agents / targets: [原文] homogeneous conceptual aquatic drones; scalability experiments use 100–1,000 drones. Intruders cross a long maritime patrol strip.
- Dynamics: simulated surface vehicles up to 10 km/h; motor outputs from recurrent ANN controllers.
- Action space: left/right motor commands plus stop-motor output; high-level arbitrator switches among `Go To Waypoint`, `Patrol`, `Pursue Intruder`, and recharge-related behavior.
- Sensing / observation:
  - local drone sensing to 200 m, implemented through short-range communication + GPS positions;
  - patrol-boundary sensors to 50 m;
  - forward camera intruder sensor to 100 m, 90° FOV;
  - camera gives detection plus relative direction, not depth.
- Communication: local, 200 m scale for neighbor alert/sensing in the model.
- Centralized/decentralized: decentralized identical onboard behavior logic; no central online task allocator.
- Map / obstacles: predefined GPS patrol-zone polygon; main lifecycle benchmark is open strip, not obstacle-rich pursuit.
- Target behavior: intruders attempt to cross the patrol zone at fixed speed (10 km/h) in the evolution task; repeated test intruders enter at random positions.
- Speed ratio: intruder and drone maximum speed are comparable in the conceptual setup.
- Capture / termination definition: **none**. The mission objective is detection and pursuit/observation; pursuit ends because the intruder exits/is no longer seen, not because the swarm captures or immobilizes it.

## 3. Core idea

### Plain-language summary
Every drone uses the same behavioral repertoire. During nominal operation the swarm disperses itself over the patrol strip. A drone that sees an intruder alerts neighbors within 200 m; those neighbors switch into the same `Pursue Intruder` behavior. If too many drones pursue, the evolved behavior causes some to stop, often leaving two trackers. The explicit high-level state machine returns a drone from `Pursue Intruder` to `Patrol` after it has not seen the intruder for five minutes. The 24-hour simulation repeatedly injects intruders every 30 minutes after the first two hours, so the same population repeatedly shifts a small fraction of drones out of and back into patrol.

### Mathematical / algorithmic mechanism
- Three evolved recurrent-ANN primitives solve navigation, patrol dispersion and intruder pursuit.
- A preprogrammed state-based arbitrator chooses the active primitive from local state/sensor inputs.
- `Patrol` fitness rewards dispersion from neighbors/boundaries and lower energy use.
- `Pursue Intruder` fitness rewards the number of drones currently detecting an intruder (capped in reward at two) while retaining the patrol/energy term.
- [AI判断] the state machine creates an explicit lifecycle even though there is no explicit coalition object or optimization variable.

## 4. Method details

### Lifecycle state-machine audit

#### State 0 — Nominal mission
- [原文, p.5] the `Patrol` behavior disperses drones to **cover the zone evenly while remaining inside its boundaries**.
- [原文, p.3] local sensing/communication allows drones to maintain coverage even when some drones fail or leave for other tasks.
- [AI判断] This is a genuine persistent area-patrol/coverage objective, stronger for CoCap lifecycle comparison than P0043’s uncommitted movement or P0046’s generic post-success patrol example.

#### State 1 — Trigger
- [原文, pp.3,5] a forward camera detects an intruder within roughly 100 m; the detecting drone alerts other drones within a **200 m radius**.
- [AI判断] This is a literal local event trigger; there is no global target-coordinate broadcast to the whole swarm.

#### State 2 — Recruitment / coalition formation
- [原文, p.5] alerted neighbors automatically activate `Pursue Intruder`.
- [原文] if several drones are pursuing, **some cease the pursuit, typically leaving only two**.
- [AI判断] This is a functional temporary pursuit subgroup with dynamic cardinality. It is not a formal coalition assignment: there is no target-wise exclusivity, utility optimization, capacity constraint, or learned capturability estimator.
- Nonparticipants continue patrolling because only the local detector/alert neighborhood changes behavior.

#### State 3 — Capture / completion
- [原文] pursuit measures continued target detection; two or more pursuers are desirable mainly for triangulation.
- [原文, p.5] when the intruder exits the patrol zone, drones stop pursuing and adjust positions with respect to neighbors.
- [AI判断] There is **no terminal capture**. An intruder may simply traverse/leave. This is tracking/pursuit, not apprehension, immobilization, no-escape closure, or proximity capture.

#### State 4 — Release
- [原文] excess pursuers can stop pursuing while the intruder is still present.
- [原文, Fig.4 / pp.5–6] the explicit arbitrator transition from `Pursue Intruder` back to `Patrol` occurs when there has been **no intruder for five minutes**.
- [AI判断] release is therefore target-loss/timeout driven, not capture-completion driven.

#### State 5 — Return
- [原文] the same drone switches back to `Patrol`.
- [原文] once an intruder has exited, pursuit behavior stops and drones adjust positions relative to neighbors; the high-level state returns after the five-minute no-intruder condition.
- [AI判断] This is strong **same-agent nominal-task restoration**. Unlike P0046, the state machine explicitly names `Patrol` as both a pre-event and successor state; unlike P0043, the return destination has an actual coverage objective.

#### State 6 — Repetition
- [原文, p.6] two hours after simulation start, intruders begin to cross the patrol zone at random locations **every 30 minutes**, for **44 crossings** over the 24-hour simulation.
- [原文] in the 500-drone case, all 44 intruders are detected.
- [原文] over the final ten hours, the system reaches a stable activity mix: roughly 79% patrolling, 14% returning/recharging, 6% going to patrol zone, and 1% pursuing.
- [AI判断] This is the strongest READ-confirmed online recurring-event loop among the four papers.

### Exact return semantics: target exit vs target loss vs timeout
The paper contains two related but distinct statements:
1. [原文, p.5] inside the evolved pursuit behavior, “as soon as the intruder exits the patrol zone, the drones stop the pursuit and adjust their positions with respect to neighboring drones.”
2. [原文, Fig.4 and arbitrator text] the high-level `Pursue Intruder → Patrol` transition is labeled **“no intruder for 5 min.”**

[AI判断] For lifecycle normalization, the **state transition back to Patrol is timeout/loss-driven**. Target exit causes detection to cease and pursuit action to stop, but terminal capture is never involved.

### Same-pool/fungibility audit
- [原文] all aquatic drones use the same mission controller and same behavior primitives.
- [AI判断] within the modeled patrol/pursuit function, the pool is genuinely fungible: a nominal patroller can become a pursuer and later become a patroller again.
- Battery/recharge creates another state, but not a fixed robot class.
- This is the most direct antecedent to CoCap’s intended role fungibility.

## 5. Evidence
- Simulation: lifecycle evaluated over 24 simulated hours in a 20 km × 0.5 km patrol zone.
- Scale: 100–1,000 drones in increments of 100; 500 drones reach 100% detection of 44 crossings.
- Metrics: detection rate, proportion of time one/two-or-more drones pursue, time-to-detection, and population counts in controller states over time.
- Lifecycle occupancy: [原文] final-ten-hour equilibrium percentages expose how much of the swarm remains in nominal patrol during repeated events.
- Real experiment: **no** lifecycle hardware experiment. [原文] hardware testbed/proof-of-concept deployment is described as ongoing/future work.
- Visual evidence:
  - Fig. 4 is an explicit mission state machine containing `Patrol → Pursue Intruder → Patrol`;
  - Fig. 6 shows 24-hour population counts across Patrol / Recharge / Go-to-waypoint / Pursue states, confirming persistent operation rather than episodic termination.

## 6. Limitations

### Author-stated [原文]
The system is simulation-centered and hardware proof-of-concept is future work; inter-drone communication exploitation is also listed as ongoing work.

### Evidence-visible [原文 + AI判断]
1. No target capture/neutralization semantics.
2. Pursuit subgroup membership is a local behavior consequence, not explicit task allocation.
3. No multi-target conflict-resolution layer is shown for simultaneous intruders.
4. No capturability or no-escape prediction determines how many drones should leave patrol.
5. Return is triggered by loss/timeout, not successful terminal capture.
6. Coverage quality is indirectly optimized/evaluated through dispersion and state occupancy rather than an event-conditioned recovery metric such as post-capture coverage deficit/recovery time.
7. Lifecycle validation is simulation only.

### Our inference [AI判断]
If terminal capture were inserted as the pursuit completion event, P0048 would become very close to CoCap’s **lifecycle architecture**. But it would still lack CoCap’s strongest possible method-level distinction: information/capturability-aware, target-wise resource allocation and support recruitment under local uncertainty.

## 8. Relation to CoCap
- Closest similarities: one homogeneous/fungible pool; persistent area patrol; local target detection; local alert recruitment; temporary pursuit subgroup; changing subgroup size; nonparticipants remain in patrol; same-agent return to patrol; repeated arrivals; long horizon.
- Fundamental differences: no terminal capture; no explicit coalition assignment; no capturability-aware recruitment; no meaningful no-escape/capture geometry; no hardware lifecycle validation.
- Does it cover a candidate novelty? **Yes** for same-pool patrol→pursuit→patrol and repeated arrivals. **No** for capture-completion-triggered release.
- Directly reusable ideas: explicit finite-state mission controller; local alert radius; event-conditioned role switching; measure population fractions in each mission state over time.
- Non-transferable assumptions: pursuit as detection maintenance only and no multi-target assignment conflict.
- New research questions exposed: CoCap’s contribution cannot be merely “dynamic gate + return to coverage”; it needs capture-completion semantics and a principled reason for **which/how many** agents leave coverage.
